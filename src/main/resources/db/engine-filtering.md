# 추천 엔진(engine) 필터링 과정

> 담당: 박상호 · 최종수정: 2026-07-31
> 룰북 전문을 읽지 않아도 엔진이 어떻게 돌아가는지 5분 안에 파악하도록 정리한 문서다.
> 상세 규칙과 예외는 「중복수혜 룰북」을 참고.

## 0. 한 줄 요약

정책 2,696건에서 **자격이 되는 것만 추리고 → 중복으로 못 받는 것을 걸러낸 뒤 → 점수를 매겨 → 함께 신청할 수 있는 3개 조합 하나**를 추천한다.

```
전체 정책 2,696건
      │  ① 자격조건 필터        나이·소득·지역·학력·전공·취업·혼인
      ▼
   후보 39건
      │  ② 중복수혜 검사        이미 받는 것과 겹치면 제거
      ▼
   상위 20건                     ③ 점수 상위 K개만 남김 (성능용)
      │  ④ 조합 생성·평가        후보끼리 충돌하는 조합은 버림
      ▼
  추천 조합 1개 (정책 3개)
```

건수는 회원 2번(경기도 거주, 28세, 월소득 207만원) + 테스트 데이터 기준 실측값이다.

## 1단계 · 자격조건 필터

DB 쿼리 한 번에서 **7개 축**을 동시에 본다. (`EngineMapper.xml` → `findEligibleBenefits`)

| 축 | 판정 방법 | 비고 |
|---|---|---|
| 나이 | 생년월일로 만 나이 계산 후 정책의 최소·최대 연령과 비교 | |
| 지역 | `benefit_region` 매핑에 회원 지역코드가 있는지 | 상위/하위 지역도 매칭 |
| 소득 | 정책이 연소득 기준이면 회원 월소득을 연소득으로 환산해 비교 | 아래 ※ 참조 |
| 학력 | `benefit_school` 매핑 | |
| 전공 | `benefit_major` 매핑 | |
| 취업상태 | `benefit_job` 매핑 | |
| 혼인상태 | `benefit.mrg_stts_cd` | 현재 데이터는 대부분 '제한없음' |

**중요한 규칙 두 가지**

- **매핑 행이 없으면 = 제한 없음**으로 해석해 통과시킨다. (예: `benefit_school`에 아무 행도 없는 정책은 학력 제한이 없는 것)
- **'제한없음' 코드**(`0013010`·`0011009`·`0049010`·`0055003`)가 매핑에 있으면 무조건 통과시킨다.

**※ 소득 조건 3가지**

| 코드 | 의미 | 처리 |
|---|---|---|
| `0043001` | 제한없음 | 통과 |
| `0043002` | 연소득 기준 | 회원 월소득 × 12 ÷ 10000 으로 환산해 비교 |
| `0043003` | 기타 (자연어) | **판정 불가 → 통과시키고 "확인 필요"로 표시** |

`0043003`은 "중위소득 150% 이하" 같은 문장으로만 들어와서 SQL로 판정할 수 없다. 걸러내면 자격이 되는 사람도 놓치므로 **일단 통과시키고 원문을 화면에 그대로 보여준다.** 대신 점수를 낮게 준다.

**마감 필터는 3중이다**

```sql
is_active = 'Y'                              -- 동기화 시점에 계산된 활성 여부
AND apply_end_date >= CURDATE()              -- 조회 시점 실시간 판정
AND aply_prd_se_cd <> '0057003'              -- 마감 코드 직접 차단
```

`is_active`는 동기화가 돌 때 계산된 값이라, API 응답에서 빠진 정책은 갱신되지 않는다. `apply_end_date` 조건이 그 지연을 메운다. 중복이 아니라 **서로 다른 층위의 방어**다.

## 2단계 · 중복수혜 검사 ★ 이 프로젝트의 핵심

### 왜 필요한가

같은 목적의 지원을 중앙정부와 지자체가 따로 운영하는 경우가 많다. 한 사람이 양쪽에서 다 받을 수 있게 되는데, 제도가 미리 "둘 중 하나만" 또는 "둘 다 받으면 금액을 깎는다"고 정해둔다.

**문제는 청년 본인이 그걸 모른다는 것이다.** 신청하고 나서야 반려되거나 환수당한다. 이걸 미리 걸러주는 게 청년타파의 차별점이다.

### 충돌은 두 곳에서, 두 방식으로 검사한다

|  | **그룹형**<br>`benefit.conflict_group_code` | **개별쌍**<br>`benefit_conflict_rule` |
|---|---|---|
| **보유 vs 후보** | 같은 그룹코드면 후보에서 제거 | 확정 중복불가면 후보에서 제거 |
| **조합 내부** | 조합에 같은 그룹이 2개 이상이면 그 조합 제외 | 조합 안에 충돌 쌍이 있으면 그 조합 제외 |

**두 축의 차이가 핵심이다.**

> **보유 축은 "정책"을 지운다. 조합 축은 "조합"을 지운다. 정책은 살아있다.**

A와 B가 충돌할 때,
- 조합 축에서 걸리면 → `A+B` 조합만 버린다. `A+C`, `B+D`는 만들 수 있다. **A도 B도 후보에 남는다.**
- 보유 축에서 걸리면 → 그 정책이 목록에서 아예 사라진다.

### 왜 미리 지우면 안 되는가

점수 높은 것 하나만 미리 남기면 **더 좋은 조합을 놓친다.**

```
A1(100점, X와 충돌)   A2(90점)   X(90점)   Y(80점)
※ A1과 A2는 같은 그룹

대표만 남기면      A1 + Y      = 180점   ← X는 A1과 충돌해서 못 들어감
조합에서 판단하면   A2 + X + Y  = 260점
```

**미리 지웠으면 260점 조합을 영영 못 찾는다.** 룰북 절대규칙 2번이 이 얘기다.

실제 데이터로도 확인됐다. 청년미래플러스(85점)는 상위 후보인데도 조합에 들어가지 않았다. 94점인 안성시 청년내일캠프와 중복불가 관계이기 때문이다. 두 정책 모두 후보 목록에는 그대로 남아 있다.

### 충돌 유형 3가지 — 처리가 다르다

| 유형 | 후보에서 제거 | 경고 표시 | 추천점수 |
|---|---|---|---|
| **중복불가** | **제거** | — | — |
| **일부제한** | 유지 | `warnings` | **20점 미부여** |
| **확인필요** | 유지 | `warnings` | **20점 미부여** |
| **외부 제도** | 유지 | `externalWarnings` | **영향 없음** |

**중복불가만 지운다.** 시스템이 금액을 임의로 차감하거나 애매한 정책을 마음대로 빼면 안 되므로, 나머지는 사용자에게 알려주고 판단을 맡긴다.

**점수는 유형이 아니라 "내부 경고가 있느냐"로 갈린다.** 추천점수의 중복수혜 항목은 `내부 경고가 하나도 없을 때만 20점`이라, 일부제한이든 확인필요든 경고가 붙으면 20점을 받지 못한다.

> 제도 안에서 충돌 가능성이 있는 정책은 유형과 무관하게 추천 순위를 낮춘다.
> 서비스 밖 제도와의 충돌은 사용자가 실제로 받는지 알 수 없어 안내만 하고 순위에는 반영하지 않는다.

### 외부 제도 경고

실업급여·국민취업지원제도처럼 **청년타파가 추천하지 않는 제도**와의 충돌이다. `trigger_benefit_no`를 `NULL`로 두고 등록한다.

비교할 대상이 우리 목록에 없으므로 **안내만 하고 제거도 점수 반영도 하지 않는다.**

다만 **사용자가 실제로 그 제도를 받는지 모른다.** 그래서 지금은 모든 사용자에게 같은 문구가 나간다. 프로필에 "현재 받고 있는 지원" 항목을 추가하면 개인화할 수 있다.

### 규칙 데이터는 어디서 오는가

**온통청년 API는 정책 간 중복수혜 관계를 주지 않는다.** 그래서 `conflict_group_code`와 `benefit_conflict_rule`은 적재 직후 전부 비어 있다.

관리자가 공고문을 검수해 직접 등록하는 구조로 설계했고, **`confirm_status='확정' AND is_active='Y'`인 규칙만 엔진이 적용한다.** 검수 전이거나 폐기된 규칙은 등록되어 있어도 무시된다.

## 3단계 · 점수 계산

정책 하나당 100점 만점. 모든 배점은 `EngineServiceImpl`에 상수로 분리되어 있다.

| 항목 | 배점 | 조건 |
|---|---|---|
| 인기도 | 10 / 7 / 4 / 1 | 조회수 1000 이상 / 300 / 100 / 그 미만 |
| 소득 조건 | 40 | `0043001` 또는 `0043002` 통과 |
| 소득 조건 | 10 | `0043003` (판정 불가) |
| 마감 임박도 | 30 / 20 / 15 / 10 | D-30 / D-90 / 상시모집 / 그 외 |
| 중복수혜 | 20 | **내부 경고가 하나도 없을 때** |

**금액이 아니라 인기도·자격 확실성·시급성으로 점수를 낸다.** `support_amount` 컬럼이 존재하지만 온통청년이 값을 주지 않아 2,696건 전부 `NULL`이기 때문이다.

점수가 높은 상위 **20개**만 조합 생성에 쓴다. 20개면 조합 후보가 1,350개 나오고, 그 이상은 계산량이 급증한다.

**정책 정렬**: 점수 높은 순 → 마감일 가까운 순 → 정책번호 오름차순

## 4단계 · 조합 생성과 평가

상위 20개로 1개·2개·3개짜리 조합을 전부 만든 뒤 충돌하는 조합을 걸러내고 하나를 고른다.

```
combinationScore = 평균 점수
                 + (정책 수 − 1) × 3
                 + (서로 다른 카테고리 수 − 1) × 4
```

단순 합계면 3개짜리가 무조건 이기고, 단순 평균이면 1개짜리가 유리해져서 절충한 값이다.

**⚠️ 이 점수는 100점 만점이 아니다.** 보너스가 붙어서 100을 넘을 수 있다(현재 102.0). 화면에 `102점/100점`이나 프로그레스 바로 표시하면 안 된다.

**조합 정렬 7단계**

| 순위 | 기준 | 이유 |
|---|---|---|
| 1 | 정책 수 많은 순 | 정책 3개 조합을 항상 우선 |
| 2 | 조합 점수 | |
| 3 | 내부 경고가 적은 순 | |
| 4 | 조합 내 최저 정책점수 | 약한 정책이 평균에 가려지는 것 방지 |
| 5 | 가장 빠른 마감일 (상시는 뒤로) | 같은 구간 안에서 시급성 구분 |
| 6 | Σ log(1 + 조회수) | 인기 정책 하나가 조합을 지배하는 것 완화 |
| 7 | 정렬된 정책번호 목록 | **결정론 보장용. 화면 노출 금지** |

7번은 같은 입력이면 항상 같은 결과가 나오도록 하는 기술적 기준이다. 사용자에게 "추천 이유"로 보여주면 안 된다.

**최종 추천은 정책 3개짜리 조합 1개다.** 정렬 1순위가 정책 수이므로, 3개짜리가 하나라도 있으면 항상 3개짜리가 선택된다. 따라서 "전체 조합 중 최적"이 아니라 **"정책 3개 조합 중 최적"** 이라고 표현해야 정확하다.

## 5. 응답 필드 (프론트 붙이는 사람용)

```
GET /api/engine/benefits/{memberNo}
```

| 필드 | 설명 |
|---|---|
| `status` | `OK` 또는 `PROFILE_REQUIRED` |
| `missingFields` | 프로필에서 비어 있는 항목 이름 배열 |
| `benefits` | 자격조건을 통과한 후보 전체 |
| `topBenefits` | 점수 상위 20건 |
| `recommendedCombinations` | 추천 조합. **정책 3개짜리 1개** |
| `warnings` | 내부 정책 간 경고 (일부제한·확인필요) |
| `externalWarnings` | 외부 제도 경고 |

각 정책에는 `score`(0~100)와 `scoreDetail`(근거 문장 10개)이 붙는다. 노종훈 멘토의 **"프로그레스 바보다 조건 충족 여부를 항목별로 보여주라"** 는 피드백을 반영한 것이다.

`scoreDetail`을 처음부터 10개 다 펼치면 답답하므로 **접기/펼치기**로 처리한다.

## 6. 알려진 한계

| 항목 | 내용 |
|---|---|
| 전역 최적이 아님 | 상위 20개로 추린 뒤 조합한다. **"전역 최적"이라고 표현하면 안 된다.** "선별된 후보군 안에서의 최적"이 정확하다 |
| 지원 금액 미반영 | `support_amount`가 전부 NULL |
| 기타 소득조건 | 328건이 자연어라 판정 불가. 자격 미달 정책이 섞일 수 있다 |
| 지역 데이터 품질 | 주관기관이 특정 지자체인데 전국 지역코드가 부여된 정책이 13건 있다. 타 지역 사용자에게 노출된다 |
| 중위소득 기준 | `household_size`를 아직 쓰지 않는다 |
| 외부 제도 경고 | 사용자가 실제로 그 제도를 받는지 모르므로 **모든 사용자에게 동일하게 표시**된다 |
| 중복수혜 규칙 데이터 | 온통청년이 제공하지 않아 관리자가 직접 등록한다. 현재 데이터는 시연용이다 |
| 테스트 코드 | 없음 |

**개선 방향** — 자연어 소득조건은 LLM으로 미리 구조화해 DB에 저장하고, 판정 자체는 기준중위소득 표를 이용한 계산으로 처리한다. 판정에 LLM을 쓰지 않는 이유는 같은 사용자에게 항상 같은 결과가 나와야 하기 때문이다.

## 7. 직접 확인하는 법

```
1. schema.sql → data_0_code.sql → data_1_base.sql → data_2_benefit_real.sql 실행
2. db/engine_test_data.sql 실행          ← 중복수혜 규칙 세팅
3. GET http://localhost:8080/api/engine/benefits/2
```

`engine_test_data.sql` 하단 주석에 **어떤 정책이 왜 제거·경고되어야 하는지, 각 정책의 실측 점수까지** 적어뒀다. 그것과 응답을 대조하면 된다.

화면으로 보려면 프론트에서 `/engine` 으로 접속.

**⚠️ MyBatis XML이나 Java를 수정했으면 서버를 Stop → Run으로 완전히 재시작해야 한다.** Redeploy나 Update classes로는 반영되지 않는다. DB 데이터만 바꿨으면 재시작이 필요 없다.
